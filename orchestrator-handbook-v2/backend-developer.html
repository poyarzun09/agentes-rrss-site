Qué no se puede afirmar todavía

No hay en el catálogo v4.0 una entrada específica de Backend Developer con purpose, tools, permissions, memory, schemas, gates, timeout o retry. El handbook anterior rellenaba estas ausencias con texto genérico; v2 no lo hace.

Restricciones arquitectónicas que sí aplican

  • Agente lógico, no un modelo dedicado por agente.
  • Scheduler controla sesiones.
  • Prompts, memoria, herramientas y permisos deben mantenerse separados por agente.
  • El esquema maestro exige allowed_tools, permissions, memory_scope, input_schema, output_schema, quality_gates, approval_policy, risk_level, timeout y retry policy.
  • Hasta que esos campos estén definidos, el rol no debería considerarse listo para activación controlada.

Ejemplo disponible en la fuente

El catálogo incluye un ejemplo completo para Code Reviewer, no para Backend Developer. Ese ejemplo demuestra el nivel mínimo esperado: herramientas explícitas, permisos explícitos, memory scope y quality gates.

Relaciones

Contains: TEAM_SOFTWARE contiene Backend Developer. No se deriva automáticamente un upstream/downstream runtime a partir de esta jerarquía.

Definition of Ready para especificar este agente

Antes de generar prompt o activar el rol, deben completarse todos los campos obligatorios de CATALOGO_AGENTES.md y PLANTILLA_AGENTE.md. Esto es un gap de especificación, no un problema de UI.
