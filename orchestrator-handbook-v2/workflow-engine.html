Workflow Engine

Componente TO-BE que separa procesos empresariales del código central y ejecuta workflows declarativos, versionados y controlados.

Qué problema resuelve

Evita codificar cada proceso como lógica ad hoc del Core. La baseline define un motor capaz de interpretar workflows declarativos con pasos, dependencias, condiciones, gates, approvals, checkpoints, handoffs y tool calls.

Límite documental: no existe todavía un schema formal completo de la API del Workflow Engine ni una state machine exclusiva del workflow.

Capacidades obligatorias documentadas

  • Pasos secuenciales.
  • Pasos paralelos controlados.
  • Condiciones.
  • Retries limitados.
  • Gates.
  • Approvals.
  • Loops acotados.
  • Checkpoints.
  • Handoffs.
  • Tool calls.
Prohibición: no permitir loops abiertos basados sólo en “seguir hasta estar satisfecho”.

Contrato de workflow documentado

La baseline contiene un ejemplo de Workflow Definition Language. Demuestra como mínimo los campos siguientes; no se presenta aquí como schema exhaustivo porque la fuente no lo declara como tal.

workflow_id: software_feature
version: 1
steps:
  - id: requirements
    agent: product_manager
  - id: architecture
    agent: software_architect
    depends_on: [requirements]
  - id: tests
    tool: run_tests
    depends_on: [implementation]
  - id: qa
    gate: qa
    depends_on: [review]

Regla: cada workflow debe versionarse y ser validable antes de ejecución.

Flujo operacional respaldado por la baseline

  1. Recibir o cargar una definición de workflow versionada.
  2. Validar la definición antes de ejecutarla.
  3. Resolver dependencias entre steps.
  4. Ejecutar steps secuenciales o paralelos controlados según la definición.
  5. Evaluar condiciones y gates.
  6. Gestionar approvals y esperas sin asumir aprobación por ausencia de respuesta.
  7. Invocar tools mediante contratos formales cuando el step lo requiera.
  8. Aplicar política de retry: primer intento → corrección basada en error → segundo intento → reviewer/especialista → humano si persiste.
  9. Persistir checkpoint cuando corresponde para soportar reanudación.
  10. Continuar o cerrar sólo si se cumplen los criterios aplicables.

Timeout / retry

RF-043 exige timeout por tool y step. RF-051 limita retries automáticos a errores retryable y a un máximo configurable. La política de retry prohíbe repetir exactamente el mismo intento sin nueva evidencia o corrección.

Checkpoint / continuidad

La baseline exige tareas largas reanudables. El checkpoint debe conservar suficiente estado para retomar de forma segura; el schema exacto del checkpoint se define en su documento especializado, no en el Workflow Engine.

Tool calls

Una tool debe declarar tool_id, versión, riesgo, schemas de entrada/salida, timeout, retries, agentes permitidos, política de aprobación y audit.

Errores

Se aplica el estándar global: code, mensaje seguro, componente, task_id, retryable, evidence/log reference y severity. La baseline no asigna aún códigos propios del Workflow Engine.

State model

SPECIFICATION GAP: existe state machine de Task, Agent y Approval, pero no una state machine exclusiva del Workflow Engine. No se hereda artificialmente una state machine para rellenar la ficha.

Audit Trail

Los eventos relevantes deben permitir responder quién, qué, cuándo, task, motivo, modelo, versión, contexto, tool, resultado, QA y aprobación. Eventos críticos: append-only.

Definition of Done

Un task sólo termina con requisitos satisfechos, artifacts completos, pruebas aplicables, QA aprobado, evidencias, findings críticos cerrados, documentación actualizada, approvals obtenidos y checkpoint final.

Trazabilidad

RF-031
Los workflows deberán ser versionables.
RF-043
Cada tool y step deberá declarar timeout. Matriz: Workflow/Tools → T-TIME-001.
RF-051
Retries automáticos limitados y máximo configurable. Matriz: Workflow Engine → T-RET-001.
RF-023 / RF-030
Tareas largas mediante checkpoint y resume. Relación textual; la matriz principal no asigna aquí un test específico al Workflow Engine.
RF-032
Tools con contratos formales de entrada y salida. Relacionado con los tool calls del workflow.
