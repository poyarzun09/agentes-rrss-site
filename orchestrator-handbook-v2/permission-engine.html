Permission Engine

Control de capacidad y riesgo que aplica mínimo privilegio y deny-by-default antes de permitir una acción gobernada.

EPIC-002 / F-006TO-BERF-010RF-011T-PERM-003

Principios
Mínimo privilegio · deny by default · separación de funciones · auditabilidad.

Objetivo operacional

La especificación de componentes indica que evalúa capacidad y riesgo. El modelo de seguridad exige permisos por agente, herramienta y recurso, límites de filesystem, comandos permitidos/bloqueados, timeouts, límites de salida y registro.

Clasificación de acciones

ClaseSignificado documental
AUTOPuede ejecutarse automáticamente dentro de la política aplicable.
SUPERVISEDAcción permitida bajo supervisión/política definida.
APPROVAL_REQUIREDDebe esperar autorización explícita.
FORBIDDENProhibida por defecto.

Flujo documentado

  1. Un agente solicita una acción.
  2. Permission Engine evalúa capacidad/riesgo y política aplicable.
  3. Si la acción requiere humano, el flujo entra en WAITING_APPROVAL.
  4. La decisión humana produce APPROVED o REJECTED; la ausencia de respuesta no es aprobación.
  5. La decisión debe quedar auditada.

La fuente exige implementar esta matriz en datos, no sólo en prompts.

Acciones críticas

  • Publicar externo: alta → APPROVAL_REQUIRED.
  • Cambiar precio: alta → APPROVAL_REQUIRED.
  • Pago/transferencia: crítica → APPROVAL_REQUIRED.
  • Borrar datos críticos: crítica → APPROVAL_REQUIRED.
  • sudo/sistema: crítica → FORBIDDEN por defecto.

Estados relacionados

La state machine documentada es la de Approval: REQUESTED, APPROVED, REJECTED, EXPIRED, CANCELLED. Task puede entrar en WAITING_APPROVAL. No existe una state machine propia del Permission Engine.

Contrato de entrada

SPECIFICATION GAP: la baseline muestra “Agent Request → Permission Engine”, pero no define todavía el schema normativo de esa solicitud.

Contrato de salida

SPECIFICATION GAP: la clasificación AUTO/SUPERVISED/APPROVAL_REQUIRED/FORBIDDEN está definida, pero no existe schema formal del objeto de decisión.

Errores

El estándar global contempla PERMISSION_ERROR y SECURITY_ERROR. Cada error debe incluir code, mensaje seguro, component, task_id, retryable, evidence/log reference y severity.

Enforcement

La seguridad debe implementarse fuera de los prompts. La matriz y controles deben existir en datos/código. El documento no define aún el formato de persistencia de reglas.
